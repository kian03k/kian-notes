# 07 · 故障恢复

> 第 7 环，也是最后一道保险。核心结论先给：**只要提交过，几乎都能救回来**；真正救不回来的是从未提交、也从未 `add` 的工作区改动。

## 7.1 心法：先留后路，再做动作

任何会动历史或工作区的操作之前，先花两秒留个锚：

```bash
git branch backup-$(date +%m%d%H%M)    # 当前 HEAD 备份成一个分支
git stash push -u -m "before-reset"    # 未提交改动（含未跟踪文件）打包
git tag backup-$(date +%m%d%H%M)       # 用标签留锚也可以
```

有了这个，后面所有操作都是可逆的。

## 7.2 reflog：一切的保险单

reflog 记录「HEAD 和分支指针被移动过的历史」，包括 commit、reset、rebase、checkout、merge。默认保留 90 天。

```bash
git reflog                  # 当前分支的指针流水
git reflog --date=iso       # 带时间，方便定位「昨天下午那次误操作」
git log -g --oneline        # 等价写法
```

输出示例：

```text
a1b2c3d HEAD@{0}: reset: moving to HEAD~2
9f3c2a1 HEAD@{1}: commit: feat: 增加导出
```

`HEAD@{1}` 就是误 reset 之前的位置。恢复：

```bash
git reset --hard HEAD@{1}          # 直接回去
git switch -c rescue HEAD@{1}      # 或先开个分支确认内容再决定
```

**分支被误删**同样能救：

```bash
git reflog                        # 找到被删分支最后一次提交的 SHA
git switch -c <分支名> <SHA>
```

## 7.3 场景速查

| 症状 | 处理 |
| --- | --- |
| `reset --hard` 丢了提交 | `git reflog` 找到原 SHA → `git reset --hard <SHA>` |
| 分支被误删 | `git reflog` 找 SHA → `git switch -c <名字> <SHA>` |
| 处于 detached HEAD 且提交了 | `git switch -c <新分支名>`，游离提交就挂上分支了 |
| rebase 到一半乱掉了 | `git rebase --abort`（回到 rebase 前） |
| merge 到一半想放弃 | `git merge --abort` |
| 冲突解决错了 | `git checkout --merge -- <file>` 恢复冲突现场重来 |
| 提交信息写错（未推） | `git commit --amend -m "新信息"` |
| 提交漏了文件（未推） | `git add <file> && git commit --amend --no-edit` |
| 误提交了大文件/密钥（未推） | `git reset --soft HEAD~1` → 修 `.gitignore` → 重新提交 |
| 误提交并已推送 | `git revert <SHA>`（安全，保留历史）；不要对共享分支 `reset --hard` + 强推 |
| 工作区改乱了想全部丢弃 | `git restore .`（**会丢**，先 `git stash` 或 `git diff > patch.diff`） |
| 暂存错了 | `git restore --staged <file>`（不丢改动） |
| 强推把远端覆盖了 | 在**本地** `git reflog` 找被覆盖前的 SHA，重建分支后重推；远端本身没有回收站 |

分支指向错乱（本地与远端不一致、`master` 要等于 `wip` 的内容）单独成篇：[[分支错乱恢复]]。

## 7.4 工作区彻底重置

当工作区被试验性改动彻底搞乱、只想要回某个分支的干净内容时：

```bash
git fetch origin
git reset --hard origin/<branch>     # 分支指针 + 工作区 + 暂存区 全部对齐远端
git clean -nd                        # 先预演：列出会被删的未跟踪文件
git clean -fd                        # 确认后执行删除
```

`git clean` **不可恢复**，务必先用 `-n` 预演。`-f` 是必需的安全阀（不加不执行），`-d` 表示连目录一起。

**不要用「删光所有文件再从分支 checkout 恢复」这种绕路做法**。它比 `git reset --hard` 多做几步，却多出两个风险：一是可能连 `.git` 一起删掉（仓库直接报废），二是被 `.gitignore` 排除的文件（`.env`、本地配置）删掉后 checkout 也恢复不了。`reset --hard` 一行就能达到同样效果且不碰未跟踪文件。

## 7.5 强推的安全边界

`--force` 系列只在自己独占的分支上用，且优先 `--force-with-lease`：

```bash
git push --force-with-lease              # 远端无他人新提交时才覆盖
git push --force-with-lease=main:abc123  # 更严格：远端 main 必须正好在 abc123
```

判定表：

| 情况 | 能否强推 |
| --- | --- |
| 自己的 feature 分支，刚 rebase | ✅ 可以 |
| 自己的分支，但已开 PR 有人在 review | ⚠️ 可以，但要在 PR 里说明「已 rebase，请重新拉取」 |
| 共享分支（团队 wip / dev） | ❌ 不可以 |
| `main` | ❌ 基本不可（平台通常默认保护） |

## 7.6 预防清单

- [ ] `main` 分支在平台上开启保护：禁强推、禁直接 push
- [ ] 每天开工先 `git fetch`，不积累分歧
- [ ] 危险命令前留 `backup-*` 分支或 `stash`
- [ ] 密钥、大文件在首推前就用 `.gitignore` / `.gitattributes` 挡掉
- [ ] 知道 `git reflog` 怎么用——这一条能救回 90% 的误操作
