# 03 · 分支模型与日常循环

> 第 3 环。目标：定下「哪条分支干什么、一天里手要敲哪些命令」，让后续所有同步与合并操作都有明确的落脚点。

## 3.1 三条线的职责

单人/小团队场景只需要三条线，不必上完整 Git Flow：

| 分支 | 角色 | 谁能推 | 允许什么操作 |
| --- | --- | --- | --- |
| `main` / `master` | 稳定线，随时可发布 | 只走 PR 合并（单人也要） | 只接受合并，不直接提交 |
| `wip` | 集成/开发线，日常干活的地方 | 自己，或小团队共享 | 提交、合并；共享时**禁止 rebase** |
| `feature/<名>` | 单功能线，从 `main` 或 `wip` 拉出 | 只有自己 | 随便 rebase、强推 |

> 一句话原则：**`main` 只进不出，`wip` 是干活的，`feature` 是一次性的。**

`wip` 是私有还是共享，直接决定能不能 rebase——这是全库最容易搞混的点，判定规则见 [[rebase与merge]]。

分支命名：

| 前缀 | 用途 | 例 |
| --- | --- | --- |
| `feature/` | 新功能 | `feature/user-login` |
| `fix/` 或 `bugfix/` | 常规缺陷 | `fix/login-401` |
| `hotfix/` | 线上紧急修复，直接从 `main` 拉 | `hotfix/pay-crash` |
| `chore/` `docs/` `refactor/` | 杂务、文档、重构 | `docs/git-guide` |

## 3.2 一次完整的日常循环

以「在 `wip` 上开发一个功能」为例：

```bash
# ① 开工前先同步，别基于旧代码动手
git switch wip
git pull --ff-only

# ② 拉功能分支（可选但推荐，功能独立时）
git switch -c feature/export-csv

# ③ 写代码 → 小步提交
git status                      # 看改了什么
git diff                        # 看内容差异
git add -p                      # 分块暂存，避免把调试代码一起塞进去
git commit -m "feat(export): 支持 CSV 导出"

# ④ 推送（第一次带 -u）
git push -u origin feature/export-csv

# ⑤ 收尾：合并进 wip，删功能分支
git switch wip
git merge --no-ff feature/export-csv
git push
git branch -d feature/export-csv
```

`--no-ff` 强制生成合并提交，让「这里合过一个功能」在历史里可见。功能分支很短、只有一个提交时可以不加强制。

## 3.3 提交粒度与信息

**粒度**：一个提交只做一件事。判断标准——能用一句话说完，且回滚它不会连带撤掉别的东西。

**格式**：`type(scope): subject`

```
feat(auth): 增加邮箱验证码登录
fix(export): 修复空表格导出时报错
docs(git): 补充分支同步流程
refactor(api): 抽出统一的请求封装
chore(deps): 升级 vue 到 3.4
```

`type` 常用：`feat` `fix` `docs` `refactor` `style` `test` `chore` `perf`。
body 里说清「为什么改」，不要重复「改了什么」——diff 已经说明了。

反例：`update`、`修改`、`提交`、`fix bug`。半年后自己都看不懂。

## 3.4 pull 的两种行为，先定策略再拉

`git pull` = `git fetch` + 二选一的整合方式：

| 配置 | 行为 | 适用 |
| --- | --- | --- |
| `pull.ff only` | 只允许快进，有分叉就报错停下 | 想让每次拉取都可预测（推荐默认） |
| `pull.rebase true` | 自动 rebase 本地提交 | 私有分支，追求线性历史 |
| 默认（未配置） | 有分叉就生成 merge 提交 | 共享分支的常规做法 |

```bash
git config --global pull.ff only      # 先设保守策略，需要 merge 时显式写出来
```

设了 `ff only` 之后遇到 `Not possible to fast-forward`，说明本地和远端真分叉了，此时要明确表态：

```bash
git pull --rebase    # 私有分支：把自己的提交重放到远端之上
git pull --no-rebase # 共享分支：生成合并提交
```

Git 2.27+ 在不配置策略时会给出提示，别用 `git config --global pull.rebase false` 一关了之，那是把选择权交给默认值。

## 3.5 动手前的三条自检

```bash
git status               # 在哪个分支、有没有未提交改动
git branch -vv           # 每个分支的追踪关系、领先/落后几个提交
git log --oneline -5     # 最近发生了什么
```

养成习惯：**任何会改历史的命令（rebase / reset / push -f）执行前，先跑这三条。**
