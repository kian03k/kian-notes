# 05 · 合并发布与版本标记

> 第 5 环。目标：把分支合进主干、把「某天的代码状态」固定成一个可复现的锚点。

## 5.1 PR 的意义（一个人也要走）

即使没有协作者，也建议用 PR 而不是本地 `git merge` 直接推 `main`，原因有三：

1. **强制看一眼整体 diff**，发现误提交的调试代码、临时文件、密钥。
2. 合并在平台侧留下**可追溯记录**：谁、什么时候、为什么合。
3. 平台能挂 CI（测试、lint），本地跑不动的东西交给它。

单人 PR 的最小流程：

```bash
git switch -c feature/export-csv
# 开发、提交
git push -u origin feature/export-csv
# 平台页面点 Compare & pull request → Create → Merge
```

## 5.2 三种合并方式，选错会污染历史

| 方式 | 结果 | 何时用 |
| --- | --- | --- |
| **Create a merge commit** | 主干多一个 `Merge pull request #N` 提交，保留分支上每个原始提交 | 分支上的提交**每个都有独立价值**，需要单独回溯/回滚 |
| **Squash and merge** | 把 N 个提交压成 1 个落进主干 | 分支上多为「fix typo」「WIP」这类过程提交（**最常用**） |
| **Rebase and merge** | 把每个提交逐个重放到主干上，无合并提交、无压缩 | 提交本身干净且线性，想要最简史 |

选择建议：

- 日常功能分支 → **Squash and merge**。主干历史只剩「一个功能一个提交」，出问题 `git revert <那一个提交>` 就能整体撤掉。
- 需要逐提交 review 或按提交粒度回滚 → Merge commit。
- 分支只有一个提交时，三种方式结果几乎一样，无所谓。

> 平台设置里可以只保留一种合并方式，避免团队成员各用各的导致历史风格不一。

## 5.3 合并后的本地收尾

平台合并完成后，本地状态是「旧」的，必须同步。以 `wip` 为开发线、`main` 为发布线为例：

```bash
# ① 更新本地主干
git switch main
git pull --ff-only

# ② 回到开发线，把主干的变化同步下来
git switch wip
git rebase main        # wip 私有
# 或 git merge main    # wip 共享

# ③ 清掉已合并的功能分支
git branch -d feature/export-csv            # 本地（已合并，安全删除）
git push origin --delete feature/export-csv # 远端
```

`-d` 只在分支已被合并时才允许删除；报 `not fully merged` 说明它还有未合并的提交，先确认再用 `-D` 强删。

合并后的同步若出现冲突，处理方式回到 [[04-同步主干与冲突解决]]。

## 5.4 标签：把某一刻固定下来

分支会往前走，标签不会。要「以后能随时回到 10 月 1 日那份能跑的代码」，用标签，不要用分支。

```bash
# 轻量标签：只是指向某个提交的指针
git tag v2026-10-01

# 附注标签：带作者、日期、说明，正式发布用这个
git tag -a v1.2.0 -m "1.2.0：导出功能上线"

# 给历史提交补标签
git tag -a v1.1.0 9f3c2a1 -m "1.1.0"

# 推送（本地标签不会自动推）
git push origin v1.2.0
git push origin --tags        # 一次推全部

# 查看与验证
git tag -l "v1.*"
git show v1.2.0
```

回到某个标签：

```bash
git switch --detach v2026-10-01     # 只读查看（detached HEAD，正常现象）
git switch -                        # 一键切回原来的分支

# 需要在标签版本上继续改，就开分支
git switch -c hotfix/from-1.2.0 v1.2.0
```

在 detached HEAD 状态下直接提交会生成游离提交，不挂任何分支，容易丢。**只读就看，要改就开分支。**

删除标签：

```bash
git tag -d v1.2.0                     # 本地
git push origin --delete v1.2.0       # 远端
```

命名约定：发布版本用语义化 `v1.2.3`（major.minor.patch），时间点快照用 `v2026-10-01`。两种混用会让 `git tag -l` 的输出难以判断。

标签与分支的取舍、更多用法见 [[git标签]]。

## 5.5 主线流程总览

```text
main    ──●──────────────●──────────────●──▶   （发布线，只进不合并）
            ╲            ╱ ╲            ╱
wip          ●──●──●──●      ●──●──●──●        （集成线，日常在这里）
                ╲    ╱
feature/x        ●──●                          （一次性，合并后删除）
                     ↑ tag v1.2.0 打在 main 的发布点上
```

## 5.6 本章检查清单

- [ ] 团队（或自己）已统一合并方式，默认 Squash
- [ ] 合并后本地主干与开发线都同步过
- [ ] 已合并的功能分支本地+远端都删了
- [ ] 有意义的发布点都打了附注标签，并且推送了
- [ ] 知道 detached HEAD 下不要直接提交
