# 04 · 同步主干与冲突解决

> 第 4 环。目标：主干前进了之后，把自己的分支安全地推到最新基线上；冲突发生时知道自己在解决什么。这是全链路里唯一需要判断力的一环。

## 4.1 先分清两个方向

| 方向 | 动作 | 谁受影响 |
| --- | --- | --- |
| 主干 → 我的分支 | 同步基线（merge 或 rebase） | 只有我的分支 |
| 我的分支 → 主干 | 合并发布（PR / merge） | 主干，所有人可见 |

本章只讲第一个方向；第二个在 [[05-合并发布与版本标记]]。两者混淆是很多流程混乱的根源——**同步是私事，合并是公事**。

## 4.2 决策：merge 还是 rebase

唯一判据是「这条分支有没有别人在用」：

```
这条分支上还有别人提交/拉取吗？
├─ 没有（私有：feature/*、自己的 wip）
│   └─ 用 rebase：历史线性，冲突当场解决，不留合并提交
└─ 有（共享：团队 wip、dev、staging）
    └─ 用 merge：不动已有提交的 SHA，别人 pull 不会炸
```

**不能对共享分支 rebase 的原因**：rebase 会重写提交，产生全新 SHA。别人本地的 `A—B—C` 和你远程的 `A'—B'—C'` 在 Git 眼里是两套东西，他一拉就是大量重复提交和冲突，严重时 `fatal: refusing to merge unrelated histories`。原理与更多取舍见 [[rebase与merge]]。

## 4.3 路径 A：rebase 同步（私有分支）

```bash
git switch feature/export-csv
git fetch origin
git rebase origin/main
```

正常情况一条命令结束。有冲突时：

```bash
git status                 # 列出 both modified 的文件
# 手工编辑，删掉 <<<<<<< ======= >>>>>>> 标记，改成最终想要的内容
git add <冲突文件>
git rebase --continue

# 中途想放弃，回到 rebase 之前的状态
git rebase --abort

# 某个提交的改动已经被上游以另一种方式实现了，直接跳过它
git rebase --skip
```

rebase 已经把分支推过远端之后，必须强推，但要带安全阀：

```bash
git push --force-with-lease
```

不要用 `git push --force`：`--force-with-lease` 会在远端出现了你没见过的新提交时拒绝推送，`--force` 会直接盖掉别人的工作。

## 4.4 路径 B：merge 同步（共享分支）

```bash
git switch wip
git pull --no-rebase origin wip     # 先和同分支的同事对齐
git fetch origin
git merge origin/main               # 把主干拉进来，生成合并提交
git push
```

想保留「何时同步过主干」的痕迹，加 `--no-ff` 显式生成合并提交；不加时 Git 能快进就快进。

## 4.5 冲突现场怎么读

文件里会出现三段标记：

```text
<<<<<<< HEAD
当前分支（你所在分支）这一侧的内容
=======
被合入分支（origin/main）那一侧的内容
>>>>>>> origin/main
```

处理步骤固定四步：**读懂两边意图 → 改成最终形态 → 删掉全部标记行 → `git add` 后继续**。

要点：

- 冲突标记是**文件内容**，不是 Git 状态。改成最终结果后必须删干净，否则会把 `<<<<<<<` 提交上去。
- 不要无脑「保留我的」或「保留他的」。多数冲突是两边各改了一半，正确解是**合并两者的语义**。
- 二进制文件（图片、xlsx、docx）冲突无法文本合并，Git 会让你二选一：`git checkout --ours <file>` 或 `--theirs <file>`。

辅助命令：

```bash
git diff --name-only --diff-filter=U   # 只列出未解决的冲突文件
git checkout --ours <file>              # 取当前分支版本（危险，会丢弃另一侧改动）
git checkout --theirs <file>            # 取被合入方版本
git merge --abort                       # 整场合并放弃，回到 merge 之前
git rebase --abort                      # 整场 rebase 放弃
```

> 注：rebase 过程中 `--ours` / `--theirs` 的语义是反的（ours 指上游基线，theirs 指你被重放的提交），容易搞错。冲突多时优先 `git mergetool` 或 IDE 的三栏视图。

## 4.6 减少冲突的四个习惯

1. **小步提交、频繁推送**。分歧积累越少，冲突面越小。
2. **每天开工先同步**。基于旧基线写一整天，晚上必然撞车。
3. **一个功能一条分支**。多人挤在同一条 `wip` 上改同一个文件，冲突是必然的。
4. **提前感知**：`git fetch origin && git status` 会提示 `Your branch is behind 'origin/main' by N commits`，不用等推送失败才发现落后。

## 4.7 可选：一条命令完成同步

把 4.3 的四步封装成带参数的别名，**不写死分支名**：

```bash
git config --global alias.up '!f(){ t=${1:-main}; git fetch origin && git switch "$t" && git pull --ff-only && git switch - && git rebase "$t"; }; f'
```

用法：`git up`（默认同步 main）或 `git up develop`。

前提是当前分支是私有的；共享分支请老老实实走 4.4，别用这个别名。
