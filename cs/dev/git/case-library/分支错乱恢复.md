# 分支错乱恢复

场景：本地分支和远端分支的指向各不相同，推拉都报错，MR 里出现一堆不属于本次改动的提交。

## 一、先别动手，先看清现状

三条命令把真实状态摊开：

```bash
git status                 # 当前在哪个分支、有无未提交改动
git branch -vv             # 本地各分支指向哪个提交、追踪哪个远端分支、领先/落后几个
git ls-remote --heads origin   # 远端各分支实际指向哪个提交（权威事实）
git log --oneline --graph --all -20   # 顺手看清分叉关系
```

常见病根：执行过 `git push origin wip:master`。这条命令把**本地 wip** 推到**远端 master**，远端 master 立刻跳到 wip 的提交上，但本地 master 没动。于是「本地 master ≠ 远端 master ≠ 本地 wip」，三方全乱。

## 二、先决定：你要「历史一致」还是「内容一致」

| 目标 | 手段 | 结果 |
| --- | --- | --- |
| `master` 的内容要等于 `wip`，历史无所谓 | `git branch -f master wip` | 两个分支指向同一提交，master 原有历史被丢弃（仍可用 reflog 找回） |
| `master` 保留自己的历史，只是把 `wip` 的改动合进来 | `git switch master && git merge wip` | 生成合并提交，两条历史都在 |

绝大多数「让 master 等于 wip」的诉求属于第一类。选第二类前想清楚：如果 wip 是从 master 拉出来的，merge 通常比直接覆盖更合理。

## 三、恢复流程（以「内容一致」为例）

```bash
# 0. 留后路，必须做
git branch backup-$(date +%Y%m%d%H%M)

# 1. 本地对齐：让 master 指向 wip 的提交
git switch wip
git branch -f master wip

# 2. 验证本地两分支确实一致
git log --oneline -1 master
git log --oneline -1 wip        # 两条输出应完全相同

# 3. 把远端强制对齐到本地（安全强推）
git push --force-with-lease origin master
git push --force-with-lease origin wip
```

`git branch -f` 不能对「当前所在分支」操作，所以要先 `switch wip` 再改 master。

## 四、为什么不「删掉远端分支再重推」

这是原始笔记给出的方案（`git push origin --delete master` + 重新 `push`），实际执行会踩三个坑：

1. **默认分支删不掉**。GitHub / GitLab 拒绝删除默认分支（提示 `Cannot delete the default branch`），流程直接卡死。
2. **中间窗口期仓库处于「无分支」状态**。这段时间内任何人 clone 都会拿到空仓库，CI 的默认分支触发器也会失效。
3. **已开的相关 PR/MR 会被关闭或标记异常**，关联的 issue 引用一起断掉。

`push --force-with-lease` 一行达到同样效果，且不影响仓库的其他元数据。它只在「远端当前指向与我上次 fetch 时一致」时才覆盖，还能挡住「同事刚好推了新提交、我一强推把它抹了」的事故。

## 五、恢复后的防复发

- **禁止** `git push origin <本地分支>:<另一个远端分支>` 这种跨分支推送。需要同步内容就本地先对齐，再正常 push。
- 每次开工先 `git fetch origin && git branch -vv`，确认自己没落后、没领先得莫名其妙。
- `main` / `master` 在平台上开启分支保护：禁止强推、禁止直接 push。这条能挡住 90% 的分支错乱。
- 分支职责要清晰：`main` 只经 PR 合入，`wip` 是开发线。见 [[03-分支模型与日常循环]]。
- 拿不准该 merge 还是 rebase 时，先看 [[rebase与merge]] 的判定规则——大部分「分支混乱」最初都是一个不该做的 rebase 或强推。

## 六、附：Windows 下清空工作区的语法坑

想「清空工作区再从某个分支恢复」时，会搜到这类 bash 写法：

```bash
find . -not -path "./.git/*" -not -name ".gitignore" -delete 2>/dev/null || true
```

在 PowerShell 里执行会直接报 `标记"||"不是此版本中的有效语句分隔符`。PowerShell 不支持 `||` 作为「忽略错误」的语法。

**但更该做的是不这么干**：删文件再 checkout 有两个真实风险——可能连 `.git` 一起删掉（仓库直接报废），以及被 `.gitignore` 排除的文件（`.env`、本地配置）删掉后 checkout 恢复不了。

正确做法一行搞定，且不碰未跟踪文件：

```bash
git fetch origin
git reset --hard origin/<branch>
git clean -nd      # 预演，看会被删的未跟踪文件
git clean -fd      # 确认后执行
```

细节见 [[07-故障恢复]]。
