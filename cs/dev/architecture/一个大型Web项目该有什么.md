# 一个大型 Web 项目该有哪些组件

> 标本：`k-food-platform` —— Spring Cloud 微服务（13 模块 / 306 个 Java 文件）+ Vue2 + TS 管理后台 + 静态门户。
> 读这个项目的收获不是"学会了 Spring Cloud"，而是**看清一个项目由哪些部件拼起来、缺哪个会死**。

## 一、先分三层，别混着看

| 层 | 回答的问题 | 典型产物 |
| --- | --- | --- |
| **交付层** | 别人 clone 下来能不能跑？ | README、`.env.example`、建库脚本、compose、启动脚本 |
| **运行层** | 跑起来需要哪些东西？ | 前端工程、网关、服务、中间件、数据库 |
| **结构层** | 代码怎么组织才不烂？ | 分层 / 分模块 / 分服务、路由装配、API 封装 |

新手看项目只看**运行层**（"用了哪些技术"），老手先看**交付层**（"能不能起来"）。
很多"技术栈很唬人"的项目，交付层是空的 —— 它只能看，不能跑。

## 二、运行层：一个请求会经过哪些部件

从浏览器点到"提交订单"，正常要穿过这条链：

| # | 部件 | 没有它会怎样 |
| --- | --- | --- |
| 1 | 静态资源服务 / CDN | 图片、JS 加载不出来 |
| 2 | 前端工程（构建 + 代理） | 页面打不开，`/api` 请求没处转发 |
| 3 | **网关** | 每个服务各自暴露端口，跨域、鉴权、限流全散落在各处 |
| 4 | **认证中心** | 登录态没法统一签发/校验；换服务就得重新登录 |
| 5 | **业务服务**（按域拆） | 所有逻辑堆一个进程，改一处全站重启 |
| 6 | **缓存**（Redis） | 热点查询直接压库；验证码/会话无处存 |
| 7 | **对象存储**（MinIO / OSS） | 视频课程图片塞数据库或本地盘，扩容即死 |
| 8 | **搜索**（ES） | 只能 `like '%xxx%'`，中文分词、相关度排序全无 |
| 9 | **消息队列**（RabbitMQ / Kafka） | 发短信、转码、审核这类慢活儿只能同步做 |
| 10 | **定时任务**（XXL-Job / cron） | 排行榜、清理、对账没地方跑 |
| 11 | **数据库** | —— |
| 12 | **注册中心 + 配置中心**（Nacos） | 服务之间找不到彼此；配置散落在每台机器 |

12 个里只要有 3~4 个，就已经是"大型项目"的形状了。
**注意 12 是横切的**：它不参与业务，却决定其余 11 个能不能互相看见、能不能拿到配置 —— 也是最容易把项目"锁死在某台服务器上"的部件。

## 三、交付层：`git clone` 之后能不能跑，看这 8 项

这是判断项目死活的唯一标准，比技术栈重要得多。

| # | 必备件 | 最小可用标准 | k-food 有吗 |
| --- | --- | --- | --- |
| 1 | `README.md` | 是什么 / 怎么起 / 起不来怎么办 | ✅（本次补的） |
| 2 | `.env.example` | 所有环境变量列出并给默认值 | ❌ 没有，且 `.env*` 被 gitignore |
| 3 | **建库脚本** | 建表 + 初始数据，一条命令导入 | ❌ **一个 `.sql` 都没有** |
| 4 | `docker-compose.yml` | 一行命令起全部中间件 | ❌ 没有 |
| 5 | 端口表 | 每个服务占哪个端口 | ❌ 端口在 Nacos 里 |
| 6 | 启动顺序 | 谁先谁后（配置中心 → 注册中心 → 业务） | ⚠️ 隐含，没写死 |
| 7 | 一键脚本 | `dev.sh` / `make dev` | ❌ 没有 |
| 8 | 默认账号 | 第一个能登进去的账号密码 | ❌ 没有 |

**8 项缺 6 项 ⇒ 这就是"技术很多但跑不起来"的全部原因。**
它不是代码写错了，是**交付件缺失**。补代码比补这些文档难十倍，所以先补文档。

## 四、结构层：代码怎么摆（三档，按规模选）

### 4.1 单体分层 —— 小项目够用

```
controller/  → 接参数、校验、返回
service/     → 业务逻辑
mapper/dao/  → 数据访问
model/       → 实体、DTO、VO
```

优点：新人 10 分钟能看懂。缺点：10 个业务域混在同一个 `service/` 里，文件数一过百就开始互相 import。

### 4.2 单体模块化 —— 中等项目的甜点区

按**业务域**切目录，每个域内部再分层：

```
modules/
├── course/    controller/ service/ mapper/ model/
├── media/     controller/ service/ mapper/ model/
└── order/     controller/ service/ mapper/ model/
```

判据：**能不能单独删掉一个域而不碰别人的代码**。能 → 分对了。

### 4.3 微服务 —— 把模块变成了进程

同样的域切分，只是每个域一个 Spring Boot 进程 + 一个库。
好处：独立部署、独立扩容、故障隔离。
代价（一定会有）：分布式事务、链路追踪、配置漂移、**本地开发要同时起 7 个中间件**。

> **判断标准**：团队 < 5 人、日活 < 1 万、没有独立扩容需求 → 单体 + 模块化足够。
> 微服务的收益是组织收益（多人多团队），不是技术收益。一个人维护 13 个模块只是把复杂度搬到了运维上。

### 4.4 前端也有"模块化"，而且长得一样

k-food 的管理后台是个很好的样板：**路由不是一张大表，而是各模块自己注册**。

```
src/module-organization/
├── index.ts      → export default class { static install(router) { router.addRoutes(RouteConfig) } }
├── router/       → 本模块路由
├── pages/        → 本模块页面
└── components/   → 本模块组件
```

`main.ts` 里四行 `Xxx.install(router)` 把空 router 拼成完整路由表。

- **好处**：加业务域 = 加目录 + 一行 install，不动别人的文件；模块可直接整块删掉。
- **对比**：集中式路由表（一个 `router/index.js` 写 200 行）在 30 个页面后就不可维护了。
- **另一种常见做法**：后端下发菜单 → 前端 `addRoute` 动态挂载（见音乐平台笔记），权限粒度更细。

### 4.5 API 层：一个实例 + 按域拆文件

```
src/utils/request.ts    → axios 实例：baseURL、超时、拦截器（token、错误码）
src/api/course.ts       → 课程域的所有接口
src/api/media.ts        → 媒资域的所有接口
```

k-food 有 **19 个 api 文件**，一个域一个 —— 这才是接口多了之后的正确姿势。
反面教材：所有接口写在一个 `api.js` 里，两百行后没人找得到。

## 五、微服务的真实代价（都是会踩的）

1. **版本必须三方对齐**：Spring Boot 2.3.7 ↔ Spring Cloud Hoxton.SR9 ↔ Alibaba 2.2.6 是一组固定搭配，随便升一个就 `NoSuchMethodError`。
2. **配置漂移**：配置放 Nacos 后，仓库里只剩 `bootstrap.yml`（只有 Nacos 地址），**仓库不再自洽** —— 换台机器就起不来。
3. **本地开发地狱**：13 个服务 + 7 个中间件，笔记本跑不动，于是大家只跑自己改的那一个。
4. **调试成本**：一个报错可能是网关、Feign、序列化、事务传播中的任意一层，日志不在一个文件里。
5. **"看起来能跑"的假象**：服务都起来了、注册中心一片绿，但白名单写成 `/**`，鉴权其实没生效。

## 六、四个"大而不精"的典型症状

| 症状 | k-food 的表现 | 根因 |
| --- | --- | --- |
| **配置外置过头** | 所有业务配置在 Nacos，仓库里没有 | 把"配置中心"当成了"配置唯一存放地" |
| **只改皮不改骨** | 目录叫 `k-food`，包名还是 `com.xuecheng`，1100+ 处残留 | 改名没做全量替换 |
| **教学 demo 混进业务** | `LoginController` 里还留着 `/r/r1`、`/r/r2` 权限演示 | 边学边写，没清理 |
| **依赖"服务器才懂"的语法** | 门户用 SSI `<!--#include-->`，本地静态服务不解析，导航直接消失 | 本地跑通的标准没有定义 |

## 七、判断项目健康度的 5 个问题

1. 新机器 `clone` 到能跑，**多久**？超过 30 分钟 = 有债。
2. 密码、密钥是写在代码里，还是从环境变量读？
3. 把仓库单独拿走（不给服务器），**配置能不能推得出来**？
4. 删掉一个业务域，要改几个文件？改得越多耦合越重。
5. 加一个新业务域，要动几个已有文件？（理想：0 个，只加目录）

## 八、下一个项目我会这么搭（最小骨架）

```
project/
├── README.md            # 是什么 / 怎么起 / 端口表 / 默认账号
├── .env.example         # 所有变量 + 默认值，真 .env 进 gitignore
├── docker-compose.yml   # MySQL / Redis /（需要才加 ES、MinIO、MQ）
├── db/
│   ├── schema.sql       # 建表
│   └── seed.sql         # 初始数据（至少一个能登录的账号）
├── server/              # 后端，按域分模块
│   └── modules/<domain>/
├── web/                 # 前端，按域分 module
│   └── src/module-*/
└── scripts/dev.sh       # 一键起全部，失败时打印缺什么
```

**前 5 个文件比任何技术选型都重要** —— 有它们，项目半年后还活着；没它们，三个月后自己都跑不起来。
