# RoCE 与无损网络

> 智算参数面的核心：RoCEv2 协议栈、PFC 与 ECN 的分工、headroom 与死锁、五平面设计、典型故障。配套题库见 [[智算网络与RoCE-题库]]。

## 一、为什么智算网络必须"无损"

AI 训练的核心通信模式是 **AllReduce**（梯度同步）：几千张 GPU 每轮迭代都要把自己的梯度汇总、再分发。

- **TCP 的丢包处理是"重传"，代价是毫秒级**（RTO 最小 200ms，即使快速重传也要几十 ms）
- **AllReduce 是同步操作，一个节点慢，全体等待**（木桶效应）
- 训练一轮迭代本身可能只有几百毫秒，一次丢包重传就让这轮翻倍

所以智算网络追求的不是"平均带宽"，而是 **P99 尾时延**。丢一个包，整个集群卡一下——这就是"无损"的意义。

**RoCE 的本质**：把 InfiniBand 的传输语义（RDMA）搬到以太网上。网卡直接读写对端内存，**不经过 CPU、不经过内核协议栈**，单次操作微秒级。

## 二、RoCE 版本对比

| 版本 | 封装 | 网络层 | 现状 |
|---|---|---|---|
| **RoCEv1** | 以太网 + 自定义 EtherType（0x8915） | 二层，不可路由 | 已淘汰，只能同广播域 |
| **RoCEv2** | 以太网 + IP + **UDP（4791）** | 三层，可路由 | **当前标准** |
| InfiniBand | 原生 IB | 专用网络 | 性能最好，但生态封闭、成本高 |

**RoCEv2 走 UDP 4791**，所以可以跨三层、可以做 ECMP——这是它能大规模组网的前提。

**为什么不用 TCP**：TCP 的拥塞控制和重传在网卡里做不了（需要完整协议栈），RDMA 要求网卡自主完成传输，所以只能靠 UDP + 自定义拥塞控制（DCQCN）。

## 三、无损的三个支柱

### 支柱 1：PFC（Priority Flow Control，802.1Qbb）

**机制**：基于**优先级**的逐跳反压。交换机某个队列快满了，向**上游**发 PFC Pause 帧，指定"暂停第 X 优先级的流量"。

```
下游队列水位 → 超过 XOFF 阈值 → 发 Pause 帧（带优先级和时间）
上游收到 → 暂停该优先级发包
水位降到 XON 阈值 → 发 XON 帧（或 Pause time=0）恢复
```

**关键点**：

- **逐跳（hop-by-hop）**：只压上游一跳，不是端到端
- **按优先级**：只暂停无损队列（比如优先级 3），其他优先级不受影响 —— 这是 PFC 比传统流控（802.3x，全端口暂停）强的地方
- **基于信任**：报文进入交换机时，要先**信任并映射**优先级（trust DSCP 或 trust 802.1p），否则 PFC 不知道该暂停谁

**PFC 的两个致命问题**：

1. **PFC 死锁（Deadlock）**：A 压 B、B 压 C、C 又压 A，形成环，全网卡死。原因通常是**路由/拓扑有环**或者 **PFC 反压跨了无损/非无损边界**
2. **PFC 风暴**：一个慢节点（比如网卡故障、GPU 卡住）持续不接收，反压一级级传回，最终**整个集群都慢**。这叫"一个慢节点拖垮全网"

**缓解手段**：
- **PFC Watchdog**：检测某端口 PFC 持续反压超过阈值（比如 200ms）→ 判定为异常 → 直接 **shutdown 该端口**（牺牲一个节点，保住全网）
- **PFC 死锁检测**：检测环路
- **Headroom 计算准确**：buffer 不够也会误触发

### 支柱 2：ECN（Explicit Congestion Notification，802.1Qau / RED）

**机制**：交换机在拥塞**早期**就给报文打标记（CE 位），接收端看到后通知发送端**主动降速**（DCQCN）。

```
队列水位超过 ECN 低阈值 → 按概率标记 CE
接收端收到 CE 标记 → 发 CNP（Congestion Notification Packet）给发送端
发送端收到 CNP → 降低发送速率
```

**配置要点（华为）**：

| 参数 | 说明 |
|---|---|
| **ECN 低阈值** | 开始标记的水位，一般设为队列的 20–30% |
| **ECN 高阈值** | 全部标记的水位，一般 40–50% |
| **标记概率** | 低阈值到高阈值之间线性增长的标记概率（最大 100%） |
| **丢弃阈值** | 超过就丢包（应该几乎不会触发，否则 PFC 之外还会丢） |

**ECN 门限设错的两个后果**：

- **设太低** → 稍微有点流量就标记 → 发送端过度降速 → **带宽跑不满**（训练变慢但没人报警，最难查）
- **设太高** → 来不及标记就撞到 PFC → PFC 反压 → 尾时延抖动

### 支柱 3：DCQCN（拥塞控制算法）

运行在**网卡侧**的算法，配合 ECN 工作：

- **加性增、乘性减**（类似 TCP 的 AIMD），由 CNP 触发降速
- 降速后**逐步恢复**（Fast Recovery → Active Increase → Additive Increase）
- 参数调优（rate reduce factor、recovery 步长）由网卡厂商提供

> 网卡侧参数（DCQCN）配错了，网络侧调优再好也没用。智算调优是**网卡 + 交换机**双侧的事。

## 四、PFC + ECN 的分工（面试核心问题）

**"为什么不能只用 PFC？"**

- PFC 是**保底机制**，代价是**反压扩散**（hop-by-hop 会让整条链路都停下来）
- 只用 PFC：一个慢节点 → 反压传遍全网 → 所有 GPU 等待 → **性能雪崩**
- ECN 是**主动机制**，让发送端在拥塞变严重之前自己降速，把拥塞**消解在水线之前**

**"为什么不能只用 ECN？"**

- ECN 是**概率性**的、有反应时间（CNP → 网卡降速需要时间）
- 突发流量（Incast）可能在 ECN 生效前就把队列打满
- 所以必须有 PFC 兜底，防止丢包

**一句话总结考试答案**：

> ECN 是主力，负责在拥塞早期让发送端降速，避免反压；PFC 是兜底，只在 ECN 来不及的情况下保证零丢包。两个都要，缺一不可：只有 PFC 会反压扩散，只有 ECN 会丢包。

## 五、Headroom（缓冲区预留）

**问题**：PFC 是逐跳的，从"下游发现快满"到"上游真的停下来"之间，**上游还在继续发包**，这段在途数据必须有地方放——否则丢包。

**Headroom 计算**（简化）：

```
Headroom = 链路速率 × 反压响应时间 × 线缆传播延迟
```

400G 链路的 headroom 需求是几十 KB 到上百 KB 每端口，8 个无损队列就是几百 KB —— 这就是为什么智算交换机要**大缓存**（几十 MB）。

**要点**：
- 线缆越长，headroom 需求越大（长距线缆要单独算）
- 端口速率越高，headroom 需求越大（400G 是 100G 的 4 倍）
- Headroom 不够 → PFC 还没生效就丢包 → "配了 PFC 还是丢包"的典型原因

## 六、五平面组网（智算集群标准架构）

| 平面 | 承载 | 带宽 | 组网 |
|---|---|---|---|
| **参数面** | GPU 间梯度同步（AllReduce / AllGather / AlltoAll） | 每 GPU 400G（8×400G/服务器 = 3.2T） | 两层 Spine-Leaf，无收敛；轨优化（Rail-optimized） |
| **样本面** | 训练数据读取（存储 → 计算） | 每服务器 2×200G / 400G | Leaf 直连存储集群，大带宽 |
| **业务面** | 平台调度、用户访问、管理 API | 2×25G / 100G | Leaf 双归 M-LAG，普通三层 |
| **带内管理** | SSH、SNMP、批量部署、Agent 上报 | 复用业务网 | 逻辑隔离（独立 VRF/VLAN） |
| **带外管理** | BMC/IPMI、交换机管理口 | 1×1G | 独立 1G 交换机，物理隔离 |

**为什么必须分开（四条理由）**：

1. **流量模型不同**：参数面是同步突发（Incast 极严重）、对丢包零容忍；样本面是持续大流量；业务面是普通南北向
2. **故障域隔离**：参数面调 PFC 出问题不能拖垮业务
3. **带宽独立规划**：参数面要无收敛，业务面可以收敛
4. **安全边界**：带外绝对不能暴露到业务网（带外是最后的救命通道）

**带内 vs 带外（最容易混）**：

- **带外**：走 BMC/IPMI，**物理独立**。服务器关机、系统崩了照样通（BMC 有独立电源和小系统）。用来远程开关机、刷固件、KVM、PXE 重装
- **带内**：走业务网 IP，依赖 OS 正常。SSH、SNMP、Ansible 下发都在这里
- 一句话：**带外是救命通道，带内是日常运维**

## 七、轨优化组网（Rail-Optimized，超节点必备）

**问题**：一台服务器 8 张 GPU、8 个 400G 网口。如果随便接到 Leaf，GPU0 到对端 GPU0 可能跨 3 跳，GPU0 到 GPU7 可能跨 5 跳 —— **转发跳数不均，时延不均**。

**轨优化的做法**：**同一张 GPU 卡号固定接到同一个"轨"（Rail）**。

```
服务器 1: GPU0→Leaf0, GPU1→Leaf1, ..., GPU7→Leaf7
服务器 2: GPU0→Leaf0, GPU1→Leaf1, ..., GPU7→Leaf7
```

这样 GPU0 → 对端 GPU0 **永远两跳**（本服务器 Leaf0 → 对端服务器），**任意两台服务器的同号卡之间的路径完全一致**。AllReduce 是"同号卡之间通信"为主，所以时延最均匀。

**超节点（Super POD）**：把柜内/柜间的高速互联做成统一的大二层（或专用互联），1024 卡甚至更多卡在一个逻辑节点内。这需要**高密交换机 + 铜缆/光缆背板**配合。

## 八、典型故障与排障

| 现象 | 可能根因 | 定位方法 |
|---|---|---|
| **训练突然变慢，无丢包** | ECN 阈值太低 / 某条链路 PFC 反压 | 看各端口 PFC 反压计数 `display interface ... pause`；看 ECN 标记计数 |
| **个别节点拖慢全网** | 慢节点（网卡/GPU/驱动问题）持续不接收 → PFC 反压 | 逐台查 PFC 反压计数，找出反压源；PFC Watchdog 日志 |
| **PFC 死锁，全网卡死** | 拓扑有环 / PFC 跨无损边界 | 查 STP/路由环；确认 PFC 只在无损队列生效 |
| **配了 PFC 还是丢包** | Headroom 不足 / 优先级映射错 / 未信任 DSCP | 看丢包计数；`display qos map-table` 确认映射；核对线缆长度 |
| **带宽跑不满** | 收敛比 >1 / ECMP 哈希不均 / DCQCN 参数太保守 | 查链路利用率分布；开内层哈希；调网卡参数 |
| **时延抖动大** | PFC 频繁触发（ECN 没起作用） | 提高 ECN 标记灵敏度（降低阈值）；检查 PFC 与 ECN 阈值是否冲突 |
| **光模块告警 / 误码** | 光功率不达标、模块不匹配、灰尘 | `display interface transceiver` 看光功率和温度；清洗/更换模块 |
| **错纤 / 弱光** | 布线错误（收发接反、极性错） | 看 CRC 错包增长；`display interface` 看 error 计数 |

**"慢节点"的定位方法**（实战核心）：

参数面所有流量都是"多对一 + 一对多"。如果某台服务器接收有问题，它的所有入向流量都会触发 PFC 反压。所以：

1. 在**所有 Leaf 上行口**查 PFC 反压计数（`display interface xxx | include pause`）
2. 反压计数增长快的端口 → 反压源就在这后面
3. 逐级向下定位到具体服务器
4. 查该服务器的网卡状态（`ibstat` / `mlx5` 计数）、GPU 温度、驱动日志

## 九、关键配置（华为 CE 系列）

```
# 1. 开启 PFC（按优先级）
priority-flow-control enable
priority-flow-control priority 3 enable

# 2. 信任 DSCP / 802.1p
trust dscp

# 3. DSCP → 队列映射（保证 RoCE 流量进无损队列）
qos map-table dscp-dscp
 input 48 output 48

# 4. 队列配置：PFC + ECN
interface 400GE1/0/1
 pfc priority 3
 qos queue 3 pfc
 qos queue 3 ecn

# 5. ECN 阈值（按队列配）
qos queue 3 ecn buffer-threshold low 30 high 40

# 6. PFC 死锁/风暴检测
priority-flow-control deadlock detect
priority-flow-control watchdog interval 100
```

**DSCP 与 802.1p 的分工**：

- **DSCP**（IP 层，6 bit）：跨三层用，全路径都要认
- **802.1p**（二层，3 bit）：只在二层有效，出三层就丢
- 智算网络**三层组网**，所以用 **DSCP** 做端到端标记，交换机 `trust dscp`
- 如果中间有纯二层设备，需要 **DSCP → 802.1p 映射**

## 十、面试口径（一段话讲完）

> RoCEv2 是把 RDMA 语义搬到以太网，走 UDP 4791，可以跨三层。它要求无损，靠 PFC + ECN 双保险：ECN 是主力，交换机在队列水位到阈值时给报文打 CE 标记，接收端回 CNP 让发送端降速（DCQCN），把拥塞消解在反压之前；PFC 是兜底，队列快满时逐跳向上游发 Pause 帧保证零丢包。只用 PFC 会反压扩散，一个慢节点拖垮全网；只用 ECN 会在突发时丢包。组网上参数面单独组网，两层 Spine-Leaf 无收敛，按轨优化接 GPU，用 eBGP + ECMP 做三层转发，不上 VXLAN——因为它没有大二层需求，封装开销和 MTU 都是负担。
